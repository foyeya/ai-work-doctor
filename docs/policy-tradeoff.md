# 尺寸政策与防污染：多大算合适，怎么改才不互相干扰

## 一、一个技能该多小？——分层的，不是一刀切

关键认知：**常驻层每轮都付钱，按需层只在用到时付钱**。所以两者该有完全不同的尺寸标准。

| 层 | 加载频率 | 建议（soft） | 硬顶（hard） | 我们当前 |
|---|---|---|---|---|
| 常驻卡 | 每轮 | ≤1300 tokens | ≤1900 tokens | **1123 tokens**（1797 字符） |
| SKILL.md 正文 | 按需 | ≤5000 tokens | ≤8000 tokens | ~2600 字符 |
| references 单篇 | 很少 | ≤120 行 | ≤300 行 | 5 篇任务协议各 40–60 行 |
| **总常驻注入** | 每轮 | ≤3500 tokens | ≤5000 tokens | persona ≈1750 + 卡 ≈1123 ≈ **2873** |

**依据（三条，按可靠性排序）**：

1. **我们自己的 A/B（最可靠，同一模型同一任务族）**
   - v2.4.x：2229 tokens / 18 条 → 用户体感"装完变笨"
   - v2.5.0：928 tokens → 变灵了，但丢了空转熔断/先复现/多假设（只在正文，没人读）
   - v2.7–2.13：1056–1123 tokens / 12 条 → 能力机制回来，体感没退化
   - 结论：**1000–1300 tokens 是当前模型的甜点区**；低于它开始丢机制，高于它开始稀释。
2. **公开文档的通行口径**：Anthropic / OpenAI / Cursor 对常驻指令的共性要求都是"短、可读、人能一眼看完"，并明确反对把整份文档塞进每轮上下文；社区实践普遍落在**几百行 / 1–2k tokens** 量级。这类文档没有精确阈值，只当方向依据。
3. **长上下文衰减的普遍现象**：上下文越长，中段信息召回越低（Lost in the Middle 一类结论），指令越多每条分到的注意力越少——这是"超 1900 tokens 开始稀释"的机制解释。

> 说明：本机 web 检索通道当前不可用（401），第 2 条是通行口径的转述而非逐字引用；第 1、3 条是可复核的自有证据与公开研究结论。

## 二、上限是护栏，不是枷锁

`eval/budget.json` 分 soft / hard 两档，并带一条**完整性优先条款**：

- 越过 **soft** → 只告警：该问"这条能不能挪进 references"，但不必立刻删。
- 越过 **hard** → `card-audit` 报错、CI 红：必须先合并或拆到 references。
- **完整性优先**：某条规则只要被 **≥2 个会话**证明修复同类失败，允许突破 soft；突破 hard 前必须先合并，**不可以为了省 token 把规则写含糊**。

一次改动值不值得，纸面算：

```
净收益 =（修复的失败次数 × 单次浪费）× 使用频率 −（新增 tokens × 每轮成本）
```

实测参照：40 个会话浪费 1,472 秒，平均每会话 ~37 秒；卡成本 1123 tokens/轮且大部分走缓存。所以一条规则**每 10 个会话省 1 分钟**就回本。

## 三、任务型分层：让"全面"不必靠加大卡

卡只放**跨任务不变式**（12 条）。任务特有的验收标准放 `references/task-*.md`，卡里只用**一行路由**指过去：

| 型 | 协议页 | 该型的完成定义 |
|---|---|---|
| 调试 | [task-debug.md](../references/task-debug.md) | 失败复现 → 根因 → 同复现转绿 |
| 实现 | [task-implement.md](../references/task-implement.md) | 接口先行 → 窄切片 → 行为验收 |
| 重构 | [task-refactor.md](../references/task-refactor.md) | 前后同测一致 + diff 半径 |
| 调研 | [task-research.md](../references/task-research.md) | 结论 + 可追来源 + 不确定项 |
| 运维 | [task-ops.md](../references/task-ops.md) | 先数后动 + 回滚点 + 复核同数 |

好处三件：**覆盖面**（每型有自己的验收）、**不串味**（按需加载、物理隔离）、**不占预算**（不加载就不花钱）。

## 四、防污染：多会话长期用不会互相干扰

| 风险 | 具体表现 | 闸门 |
|---|---|---|
| 膨胀/串味 | 一个调试任务的教训强加到重构任务 | 任务型协议隔离；卡只放不变式 |
| 过时 | 两个月前的失败模式不复现，规则还留着 | 采样窗口 14 天 + 不复现就撤 |
| 自我强化 | 规则导致行为 → 行为产生"证据" → 反证规则对 | `distill` 只产提案，永不自动改 SKILL.md |
| 旧卡考古 | 拿 v2.0 会话证明"新规则没用" | 提案区分「新卡仍命中」与「旧卡考古」 |
| 一次连坐 | 一条坏规则拖垮整套 | 一条规则一个 commit，`git revert` 单条 |

## 五、这些政策怎么被验证

- `card-audit.ps1`：结构 + 19 条语义条款 + **预算闸门**（字符/条数/块行数）
- `distill.ps1`：提案末尾自带成本闸门与防污染两张表
- 每次发版：同批会话复跑，失败数不降就回滚

> 一句话总结：**上限设在高位当护栏，不设低当紧箍咒**；想加能力，先证明它值得，再决定放卡还是放 references。
