## 1. 诊断：压缩后具体会丢什么
### 1.0 先把机制说准（决定了规则能不能生效）
依据 DSH 宿主源码（`C:\...\npm\node_modules\@deepseek-ai\dsh`，`dsh-compaction-basic/README.md`）：
- 压掉的是**旧的对话历史**：最旧的"平衡段"被替换为一条 user 消息，内文用 `<compacted-summary> … </compacted-summary>` 框住（README.md:119、:167）。近期尾部逐字保留。
- **常驻卡不会被压缩**——`system/message` 在 surface node 0，选区永不覆盖它（README.md:113）。所以"卡里写什么"决定压缩后还剩下什么纪律，这是本方案唯一可靠的地基。
- 伴随的 checkpoint preamble 原文是：
  > "Treat the captured context as established background and build on it **without restating it**. Continue the task directly from the messages that follow, **without acknowledging this checkpoint**."（README.md:172）
  → **这条 preamble 与"压缩后必须先输出 REANCHOR"直接冲突**（一个让你别重述，一个让你必须重述）。详细协议里必须显式写出优先级，否则规则会被压着打。
- 可选的 `dsh-compaction-tool-result-pruner` 会先把超长工具输出剪成"头 4096 + 中部剪除标记 + 尾 1024"（>8192 字符时），**原结果留在 session log，不再进模型上下文**（pruner README:48、:117）。→ 命令输出的"行号/端口/PID 原文"正是被剪掉的那部分。
- `/compact` 可手动触发（`dsh-command-compact`），这是 §5 验证方法的抓手。
- 压缩用一个**额外模型调用**产出摘要，只有返回文本进检查点（README.md:119）——即"总结一次丢一层细节"是宿主级事实，不是模型偶发失误。
### 1.1 六个具体丢失场景（都能指认现场）
| # | 丢什么 | 现场对话长什么样（例） | 压缩后模型实际做了什么 |
|---|---|---|---|
| D1 | **硬约束的字面值** | 用户第 2 轮说："服务端口固定 **18080**，别用 3000；配置只改 `C:\Users\Administrator\Desktop\proj\config\app.yaml`；禁止动 `data\` 下的东西" | 摘要写"用户要求用某个端口并修改配置文件"→ 模型起了 3000、改了 `app.yaml` 的副本、顺手删了 `data\tmp` |
| D2 | **已改文件 + 行号** | 第 9 轮已把 `src\auth\login.ts:118–124` 的 token 校验改完，笔记在对话里 | 摘要只剩"已经改过登录逻辑"→ 重读整文件（违反 R3 只读 2 次），或拿**旧行号**去 patch（R3 反例 L110），改错位置 |
| D3 | **失败尝试与失败原因** | "`npm i sharp --registry=npmmirror` 失败：node-gyp 找不到 VS 生成工具；`--build-from-source` 也失败" | 摘要只剩"装 sharp 遇到问题"→ 换个写法**再失败 3 次**，每次 3–5 分钟，直至撞 R6 上限 |
| D4 | **机器特定结论**（R1 探测结果） | 开头探到"本机无 `rg`/`grep`，PS 5.1，控制台 936" | 结论被压掉 → 重新探测（违反 R1），或直接写 `rg`/`sed | head` 命令（R14 高频坑），一条条试错 |
| D5 | **未完成清单项** | 用户给了 6 步清单，环境探测/改配置/重启服务已完成，剩①加开机自启 ②回滚脚本 ③交付说明 | 摘要倾向保留"最近发生的事"，清单**尾部项整条蒸发**→ 交回来少了 2 项，且用户不看摘要发现不了 |
| D6 | **已验证结论的正确性范围** | "已验证：`curl 127.0.0.1:18080/health` 返回 200，且 `scripts\deploy.ps1:44` 的 `-Env` 默认值已生效" | 摘要只剩"部署完成"→ 压缩后再"验收"一次（违反 R5 的"已给运行时证据"），甚至把参数改回去重跑 |
| D7（附带，工具输出剪除） | **命令输出的原文**（PID/端口/行号/报错码） | `Get-NetTCPConnection` 的输出、编译报错前 12 行 | 剪枝后中部消失 → 引用不存在的 PID、报错码记成相近的另一个 |
> 共同结构：**摘要保留"做了什么"的动词，丢掉"什么值/在哪/为什么失败"的名词**。规则要做的不是"让摘要更好"（宿主的事），而是**把不可再生的名词挪出被压缩的区域**。

## 2. 建议进常驻卡的行（**限 1 行**，逐字可粘贴）
### 2.1 唯一的一行（R15，压缩/接管后重锚 + 账本，逐字可粘贴）
```
15. **压缩/接管后重锚 + 账本**：上下文里出现 `<compacted-summary>`，或本轮靠摘要/交接接续（用户消息缺「对象+动作」时仍先走第 0 条）→ 动工具前先读账本 `.aiw/ledger.md`（存在则读 1 次 / ≤60 行，缺失则跳过），并用一行输出 `REANCHOR: 目标 / 硬约束(≤3，含端口·路径·禁止项) / 已改(≤10，一律"路径:行") / 未完成项(≤5) / 失败(≤3)`（总长 ≤200 字，改写或推断来的值标 `?`）；账本只在改完文件或一次失败后追加，单次 ≤2 行、总量 ≤40 行，用户没预置 `.aiw/` 就不建任何文件、只提一句请其建。

**配平做法（见 §2.3）**：卡片末尾的固定回执行**不用改**——`REANCHOR: 目标 / 硬约束 / 已改 / 未完成项 / 失败` 的字段定义就写在第 15 行内部（自包含，不再增加跨行引用），回执行保持原样。
**为什么这 1 行比第 2 候选更值**（三个候选都实测过字数/行数权衡）：
| 候选 | 内容 | 判定 |
|---|---|---|
| **A（推荐，上面这一行）** | 压缩后读账本 + 印 `REANCHOR`（含字面值字段），账本写入点压成从句 | ✅ 唯一同时给"止损动作"和"数据来源"的一行；触发条件全在**常驻卡**里（不会被压缩），所以压缩后 100% 可见 |
| B | 只写"账本写入点"（何时落盘、路径、上限），把 REANCHOR 放正文 | ❌ 压缩后没人读得到"要重锚"这条指令；账本写了也不会被读，等于只增加了磁盘文件 |
| C | 把 5 个字段的完整模板内联进卡 | ❌ 卡片每条限 1 行、禁代码块（CONTRIBUTING 第 2 条），且账本正文属长文本，塞进常驻卡会挤掉硬规则 |
**它值这 1 行的四条理由**：
1. **只有常驻卡能穿越压缩**：宿主压缩把旧历史换成 `<compacted-summary>`，而 node 0 的系统卡永不被压（§1.0）。触发条件写在这里，压缩后才一定看得见；写进正文 `references/` 或对话里的规则，压缩后大概率不会被打开。
2. **它独占一个别的规则都没有的触发面**：R0 管"消息里没对象"、R13 管"人不在"，没人管"模型的记忆刚被替换过"。这正是 D1–D6 六个事故的共同成因。
3. **回执可判定、成本固定**：一行、≤200 字、5 字段、每个字段有数字上限（≤3/≤10/≤5/≤3），用户扫一眼就能验收；相对每轮都在上下文里的常驻成本，它只在压缩后那一次付出输出成本。
4. **默认不落盘**：账本开关写成"用户没预置就不建文件"，满足"不污染用户工作区"这条硬约束，短任务零成本。
### 2.2 必须配套写进 `SKILL.md` 正文的一条（否则回执会与宿主指令自相矛盾）
正文新增 **R15 压缩后重锚 / 账本**，至少包含三句：
1. **优先级**：R15 只处理"已被压缩或靠摘要接续"的上下文；用户消息仍缺「对象+动作」时 R0 依旧优先（"继续"单独出现时先按 R0 问一句，但问的时候要把 REANCHOR 的字段一起列出来，省一轮）。
2. **与 R13 的分工**：R13 的 `CHECKPOINT` 治"无人值守时用户看不见进度"，R15 的 `REANCHOR` 治"压缩后模型自己记不住"。二者触发不同、载荷不同（REANCHOR 必须含**字面值**：端口/路径/禁止项），允许同一轮各印一行，但**不许合并成一行**——合并后字面值字段会先被省略。
3. **与 preamble 的冲突裁决**：宿主 checkpoint preamble 要求"不要重述检查点"，本规则要求逐字重述`目标/硬约束/已改/失败/未完成项`；裁决为**以 R15 为准**，且 REANCHOR 只印一行、印完立即继续干活，不写任何解释或道歉。

**行数口径**（与 CI 一致：`sed -n '/AIW_CORE:START/,/AIW_CORE:END/p' | wc -l`，已在本机实测 = 22）：

**R7 + R8 合并后（逐字可粘贴，替换原卡第 7、8 行）**：
```
7. **进程端口收口 + 只杀自家进程**：后台进程（dev server / watcher / 监听）先记 PID + 端口 + 日志文件；kill 前用 `Get-Process -Id <PID>` 核对命令行，非本次启动的先问用户；禁止 `taskkill /IM`、`pkill -f`、`killall`；收工前 `Get-NetTCPConnection -LocalPort <port> -State Listen` 应为空，不留就写明还留着哪个 PID。

## 3. 建议放按需文档：`references/iq-ledger.md`（账本协议 + 模板）
> 放这里的理由与现有设计一致：常驻卡只放"触发 + 动作 + 上限"，协议与模板命中症状才读（同 `references/desktop-cn.md` 的定位）。
### 3.1 账本放哪、叫什么（判据与"为什么不是别处"见 §3.4-1）
| 项 | 决定 |
|---|---|
| 默认路径 | `<项目根>\.aiw\ledger.md`（固定名，不按日期/任务分片——分片会让"压缩后先读哪个"变成新决策） |

### 3.2 什么时候写（这是防污染的关键：默认不写）
- **写**：① 压缩后重锚时（补全字段）；② 改完一个文件（追加一行 `路径:行`）；③ 一次尝试失败（追加 ≤60 字符原因）；④ 清单项完成/新增；⑤ R13 的 `CHECKPOINT` 时刻。
- **不写**：每次工具调用后、每次读文件后、探测环境后（探测结论只在 R1 那一次写 1 行）。
- **键位选择**：默认**不主动创建 `.aiw\`**。判据两条（任一满足才写）：用户预置了 `.aiw\` 目录，或用户说过"记一下/记账本/落盘"。否则只在对话里印 REANCHOR，并加一句"要不要我落个账本（一行命令）"。
- **写入成本上限**：单次追加 ≤2 行；同一轮最多写 1 次；账本总量 ≤40 行，超了就把"已完成"字段折叠成一行计数（`已完成: 7 项（明细见 commit/log）`），禁止把历史当档案堆。

### 3.4 最小侵入性：放哪 / 叫什么 / 何时写 / 怎么关 / 卸载怎么清
> 补充要求五项，逐项落死。**卡片行里只保留最必要的一句**（"默认 `.aiw/ledger.md`…用户没预置就不建任何文件"），其余全在本文件。
1. **放哪**：`<项目根>\.aiw\`（`%AIW_LEDGER%` 或用户明说可覆盖）。
   - `.aiw\` 是"被忽略的目录"：卸载/清理只需删一个目录，不留散落文件。
2. **叫什么**：目录 `.aiw`、文件 `ledger.md`（固定名，不按日期/任务分片——分片会让"压缩后先读哪个"变成新决策，反而丢信息）。若用户要求单文件可读性，允许同时放一个 `.aiw\ledger.md` 的目录联接，但**默认只此一个**。
3. **什么时候写**（默认关闭是防污染的关键）：
   - **写**：① 压缩后重锚补全字段；② 改完一个文件（追加 `路径:行`）；③ 一次尝试失败（≤60 字符原因）；④ 清单项完成/新增；⑤ R13 的 `CHECKPOINT` 时刻。
   - **不写**：每次工具调用后、每次读文件后、环境探测后（R1 结论只写 1 行）。
   - **门槛（任一满足才创建）**：用户预置了 `.aiw\` 目录，或用户说过"记一下 / 记账本 / 落盘"，或 `AIW_LEDGER` 已指向路径。否则只在对话里印 `REANCHOR`，并附一句"要不要落个账本"。
   - **写入上限**：单次追加 ≤2 行；同一轮最多写 1 次；总量 ≤40 行，超量折叠（`已完成: 7 项（明细见 commit/log）`）；禁止全量重写。
4. **用户不要时怎么关**：三档，逐级更"硬"——
   - 静默不建：什么都不做（默认行为）；
   - `setx AIW_LEDGER off`（或会话内 `$env:AIW_LEDGER='off'`）：本机后续会话都不落盘；
   - 账本首行 `<!-- aiw-ledger:off -->`：文件还在但停止写入（适合"先留着，别再动"）。
   三档都不需要改代码、不需要重装。
5. **卸载时怎么清**：本插件的 `-Uninstall` **只删标记块，不动 `.aiw\`**（符合它"用户原文逐字还原"的承诺）。所以：
   - 清账本是一条**独立命令**，由用户执行：`Remove-Item -Recurse -Force .aiw`（先确认路径，参见 R10/R11）；
   - `INSTALL.md` 与 `SECURITY.md` 必须写明"本插件可能在你项目里留下 `.aiw\ledger.md`，卸载不会删它"，并在卸载输出的最后一行提示该命令；
   - 可选（需用户明确确认，属 R11 闸门）：安装脚本加 `-PurgeLedger` 开关，先打印 `IMPACT: 将删除 <路径>\.aiw` 再等确认；
   - `.gitignore` 那行也由用户撤销（`Add-Content .gitignore "`n.aiw/"` 的逆操作 = 删掉该行）。

| 风险 | 评估 | 缓解 |
|---|---|---|
| 误提交密钥 | 账本会记命令与路径，容易顺手粘 token | §3.3 已把 R12 扩到账本（`<TOKEN>` 占位符）；落盘前自查 `sk-\|AKIA\|ghp_\|PRIVATE KEY` 应 0 命中，且账本里**禁止写 PID**（跨轮次无效，会诱发 R8 违规） |
| 变成新的烧 token 源 | 每步全量重写 = 又一个上下文黑洞 | 只追加、≤2 行/次、总量 ≤40 行、超量折叠 |
| 卸载残留 | 用户不知道机器上多了文件 | §3.4-5：文档声明 + 独立删除命令 + 可选 `-PurgeLedger` |
| 短任务收益为负 | <10 轮的任务根本不会触发压缩 | **默认关闭**（§3.4-3 门槛）→ 短任务自动零成本 |
**结论**：值得做，但只值"默认关闭"这一档。压缩是宿主行为、不可避免；把 5 个字段固化到磁盘是唯一不依赖模型记忆的手段。默认关闭后，成本只由真正长任务（部署/重构/逆向/爬虫）承担。
### 3.5 反向检查表（每次 REANCHOR 后自问 3 句，放文档末尾）
1. 我这轮要用的**端口/路径/命名**，是从账本或用户原消息读的，还是从摘要"想起来"的？
2. 我要动的那几行，**行号**是账本里的，还是猜的？（猜的 → 先比哈希/改看函数名定位）
3. 我是不是正在重做账本"失败尝试"里已经失败过的写法？

## 4. 反例：让细节丢得更快的做法
| 反例 | 为什么更糟 |
|---|---|
| **结论只留在对话里**（"我已经确认端口是 18080 了"） | 被压缩的正是这段对话；摘要只留动词。等价于没确认过 |
| **用模糊行号**（"鉴权逻辑在文件中部"｜"大概 120 行左右"） | 压缩后 120 行可能已被上一次改动挪走；R3 正文 L110 已把"拿旧行号 patch"列为反例。必须 `路径:行`，并附哈希/mtime |
| **把 REANCHOR 写成叙述段落**（"压缩后我重新梳理了一下，目标是…"） | 占用尾部预算、下一轮又会被压；且没有可判定字段，用户无法验收。固定一行、固定 5 字段才有用 |
| **压缩后不重锚就继续干** | 这是缺省行为，也是 6 个场景的成因；preamble 还在旁边鼓励它"别重述" |
| **相信摘要里的"约束"字段**（"摘要说要用 18080"） | 摘要可能写的是"某个自定义端口"。字面值只认用户原消息与账本 |
| **只总结、不验证**（"总结显示已完成"就跳过 R5） | 把压缩摘要当成了运行时证据，直接违反 R5；D6 就是这么发生的 |
| **账本全量重写** | 账本本身变成被裁剪/被压缩的对象，还额外烧 token |
| **账本写 PID / 端口占用 / token** | PID 跨轮次无效（会误杀，违反 R8）；token 落盘违反 R12 |
| **把账本放进 `~/.codex`、`~/.dsh`** | 污染宿主全局指令目录，破坏 `-Uninstall` 的逐字还原承诺（`validate.yml:78` 那条自测会失守） |
| **强制每轮都写账本** | 短任务被强加文件；用户抱怨"我就问个问题你建了个目录"——本插件最忌讳的越界 |
| **把"清单项"只记在摘要里** | 摘要对尾部清单项最不友好（D5）；清单必须落成 `[ ]` 列表 |

## 5. 可验证方式：怎么制造一次压缩并检查是否丢细节
### 5.1 制造压缩（三种，从易到难）
1. **手动（推荐，5 秒）**：DSH 里挂 `dsh-command-compact`，对话中直接输入 `/compact`（README.zh:86）。压缩完成会报告"压缩了多少历史项 + 估算释放 token"。
2. **压力触发**：把 `dsh-compaction-basic` 的 `thresholdRatio` 调低（如 0.3），多轮后自动压缩（config 表见 README.zh:60–78）。
3. **硬核版（最接近真实事故）**：压缩后**开一个新会话**，只把 `<compacted-summary>` 那段摘要粘进去，问同一组探针问题——这模拟"摘要就是全部上下文"，能直接量出细节丢失率。
### 5.2 压缩前布桩（否则无从判定）
在压缩**之前**故意让对话里存在 6 类事实（对应 REANCHOR 的 5 个字段 + 机器结论），且**只在对话里**（不要提前写账本，这样 A 组才测得出纯损失）：
- 用户消息里的端口 `18080`、路径 `…\config\app.yaml`、禁止项"别动 `data\`"
- 已改行号 `src\auth\login.ts:118-124`
- 一次失败尝试（含原因）
- 6 项清单（已完成 3、剩 3）
- 一条 R1 探测结论（无 `rg`）
- 一条已通过的验证（`/health` 返回 200）
### 5.3 压缩后探针（5 问，可客观打分）
```
REANCHOR: 目标=? 硬约束=? 已改=? 未完成项=? 失败=?
```
1. 端口号是多少？配置文件的**完整路径**？（期望逐字 18080 / 完整路径）
2. 已经改过哪些文件、**哪几行**？（期望 `路径:行`）
3. 之前哪条命令失败过、失败原因？（期望 ≥1 条含原因；期望**不再重试**同一写法）
4. 用户的清单还剩哪几项没做？（期望逐项列出）
5. 本机有没有 `rg`？已经验证过的结论是什么（探针命令 + 期望值）？
**判定**：6 类事实里错 1 项记 0.5，全对=1.0。A 组（无账本）、B 组（预置 `.aiw\ledger.md` 并按 §3.3 维护）各跑 3 次取平均。
### 5.4 具体可观测的验收信号
- **行为信号**（比自述可信）：压缩后是否**重复读了已改文件整篇**（R3 违反）、是否**重试了失败命令**（D3）、是否**重跑了已验证的探针**（D6）。前两项能从工具调用日志直接数出来。
- **回执信号**：`REANCHOR:` 行是否出现、是否 5 字段齐全（目标/硬约束/已改/未完成项/失败）、是否被改写项打了 `?`、是否 ≤200 字。
- **文件信号**：`.aiw\ledger.md` 的字段完整度 + 是否 ≤40 行（防"账本自己膨胀"）。
- **回归保护**：把 5.3 的 5 问做成固定脚本/固定 prompt 模板，进 CI 或 issue 模板（现有 `validate.yml` 只能验静态行数与关键字，验不了行为）。
### 5.5 触发条件的可移植性（别的宿主不叫 `<compacted-summary>` 怎么办）
- DSH 口径**有确切标记**：`<compacted-summary>`（`dsh-compaction-basic` README.md:119/:167），所以 R15 的第一个触发词是**可直接字符串匹配的**。
- 其它宿主（Claude Code / Codex CLI / Cursor 等）压缩后不一定给这个标记。兜底触发词已在 R15 里写成"**或本轮靠摘要/交接接续**"——判据是模型自检三问：① 我这条对话的开头是不是一段"总结性叙述"而不是原始用户消息？② 我记不清某个端口/路径的**字面值**吗？③ 我是否刚被要求"基于前面的结论继续"？任一为真即按 R15 执行。
- **这条兜底是推测，不是依据**：别的宿主的压缩实现与标记我没核（只核了 DSH）。若维护者要覆盖多宿主，建议先按 §5.3 在各宿主实测一遍"压缩后能不能自检出被压过"，再决定是否把兜底判据写进 `references/iq-ledger.md`。
