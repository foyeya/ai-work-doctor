# 任务型协议：调试（bug / 故障 / 偶发）

> 命中即读：多步任务里出现"报错、跑不通、时好时坏、性能退化"时加载本页。
> 卡内总纲：第 1 条（先复现再修）+ 第 2 条（多假设诊断）。

## 完成定义（缺一项就不算完）

1. **有一条会失败的复现**：命令或用例，改之前跑一次能看到失败（贴原样输出）。
2. **根因位置**：`file:line` + 一句话机制（为什么这行导致这个现象）。
3. **修复后同一复现转绿**：同一命令重跑，贴输出。
4. **回归范围**：受影响的调用方/测试是否跑过（`RIPPLE: 命中 N 已改 M`）。

## 3 个检查点

- **CP1 先二分定位，再读代码**：现象 → 缩小到文件 → 缩小到行；不要一上来通读整个仓库。
- **CP2 假设要写"怎么排除"**：每个假设必须绑一条能证伪的命令；排除不掉的假设不许当结论。
- **CP3 偶发问题只认证据**：日志行号、时间戳、复现次数；`run.log` 里的行号可能与代码漂移，必须回代码核对。

## 常见翻车

| 翻车 | 症状 | 正确做法 |
|---|---|---|
| 改症状不改根因 | 报错消失但数据错了 | 问"谁把坏数据写进去的" |
| 只修主路径 | 主流程好了，后台任务仍炸 | 搜同名调用方，报 RIPPLE |
| 靠"再试一次" | 同一个 flaky 结果重复 3 次 | 第 3 次换手段（加日志/加断言/换输入） |

## 退出条件

修好且回归通过 → 交付；复现做不出 → 说明缺什么信息（日志/环境/时间窗），**不要**声称"已修复"。
